# FedEx Toggle Enable List

Turns the store-scoped toggles from a release's cards into the exact text the dev team pastes to enable them for one or more merchant shops.

## Inputs

- One or more shop domains (the merchant's `*.myshopify.com` store, or whatever domain the card evidence uses — not a Trello or card id).
- A scope: a release name/guide already generated by `fedex-handoff-docs` (preferred — reuse its index table), or a Trello list/lane to read directly if no guide exists yet.

## Steps

1. **Get the toggle list per card.**
   - If a combined support guide already exists for this release (`data/handoff_docs/...md`), read its `Included Story Cards` index table — the `Toggle Name` column lists the exact per-card toggle key(s), comma-separated when a card has more than one.
   - Otherwise, pull the lane's cards via `fedex-trello-operator` and run `build_handoff_context` / `detect_toggles` from `pipeline/handoff_docs.py` the same way the handoff-docs skill does, then take `ctx.toggle_names`.
   - Skip cards whose toggle is `None` / not detected.

2. **Classify each toggle key — FedEx cards are inconsistent about this, so check each one individually, don't assume a single shape:**
   - **Domain-prefixed form**: the key starts with `{shop}` or a literal example domain, sometimes followed by a literal `.myshopify.com` before the flag suffix (e.g. `{shop}.myshopify.com.postalcode.required.countries`, or `{shop}.bulk.edit.dimensions.enabled` with no `.myshopify.com`). Replace only the `{shop}` placeholder (or the literal example domain) with the requested shop domain; keep any literal `.myshopify.com` in the key exactly as written in the card evidence — do not add or remove it.
   - **Bare form**: a flag name with no shop prefix at all (e.g. `product.status.enabled`, `bulk.edit.dimensions.enabled`). These are scoped by the store parameter passed alongside the flag, not by a string prefix. Do not invent a domain prefix for these — list them separately as "not domain-keyed; apply against the named shop directly" rather than folding them into the substituted block.

3. **Validate every given shop domain before substituting.**
   - Expect something that reads as a real store identifier (a `*.myshopify.com` subdomain, or the exact domain form the card evidence used). Flag anything that looks incomplete, has stray whitespace, or is missing the domain suffix the card evidence expects — state exactly what looks wrong rather than silently normalizing it.

4. **Emit the result** as a fenced code block, one line per domain-prefixed toggle, in the same key:value shape the card evidence used for that toggle (preserve `.myshopify.com` where the evidence had it, omit it where the evidence didn't):
   ```
   "<shop-domain>.<flag>": true,
   ```
   Group by shop, in the order given. If multiple shops were requested, repeat the block per shop with a heading naming which shop it's for.

5. **List anything left out** — bare-form toggles, or anything you could not confidently generalize — with a one-line reason each, including the note that bare toggles apply per-store rather than by key string.

## Guardrails

- Never invent a toggle not backed by actual card/comment evidence.
- Never silently repair a malformed or incomplete shop domain.
- This skill only produces text. There is no toggle-write API in this repo — enabling a toggle happens outside this pipeline. Do not claim or imply anything was enabled.
- If the user also wants this sent to the dev team, treat it as a Slack send under the same approval rules as the handoff-docs skill's delivery flow: show the content and target first, send only after explicit approval unless the destination was already named in the same request.

## Final Response

Return the fenced code block(s) exactly as specified above, plus the exclusion list from step 5 if non-empty. Do not add explanatory prose inside the code block itself — the dev team pastes it as-is.
